### この仕様書の位置づけ

v3 仕様書 §3.4「既知の品質差」で MVP として許容した「チャンク末尾の部分ページ」について、**分割境界の選定を改善して読み味を改善する**。v3 §6 で非目標とした「部分ページを詰め直す PDF 再組版」は引き続き行わない。

## 2. 背景と問題

4分割フォールバックは各チャンクを独立した PDF としてレンダリングし、`pdf-lib` でページ単位に連結する（`src/aozora-fallback/merge-pdf.ts:56-65`）。テキストの流し込み直しは行わないため、**チャンク境界は必ずページ境界になる**。チャンク末尾のページは途中までしか埋まらず、残りは余白のまま確定する。

v3 §3.4 の実測では、chunk 0 の最終ページに本文が4〜5行だけ残り、以降が空白だった。1,249ページ中3箇所。

問題は余白そのものではなく、**その余白がどこに落ちるか**である。現行実装は境界を「文の切れ目」に置こうとするが、後述する3つの欠陥により、実際には**行の途中**や**章の途中**で切れている。読者からは「意味が続いているのにページが飛び、次のページの頭に数文字だけ残る」ように見える。

### なぜ PDF 側で直せないか

`pdf-lib` にはページ内の描画内容（テキストの有無、占有領域）を検査する API がない。ページサイズ（`getWidth`/`getHeight`）とページ数しか取得できず、「最終ページがどれだけ埋まっているか」を測る手段がない。したがって結合後に余白を詰める後処理は実装できない。**打てる手は分割位置の改善に限られる**。

## 3. 実測結果

失敗事例である「神曲 02 浄火」（`https://www.aozora.gr.jp/cards/000961/files/42184_16641.html`）の `div.main_text` を、リポジトリの `splitContentIntoChunks()` にそのまま通した実測値。

|---|---:|
| `computeFragmentMetrics` 基準の textLength | 186,948 |
| `<br>` の総数 | 4,955 |
| `<ruby>` の総数 | 2,711 |

| 指標 | 値 |

浄火は「本文（前半47%、各曲頭に改ページ注記）」と「注釈・解説（後半53%、改ページ注記なし）」の2部構成。したがって **`［＃改ページ］` だけに頼ると 75% 地点で候補が枯れる**（最寄りが 47.19%、27.81% のずれ）。連続 `<br>` は全域に分布し、最大ギャップが 2.70% しかないため、どの目標位置の近傍にも必ず候補がある。

### 3.3 現行実装が実際に選ぶ境界

`src/aozora-fallback/split.ts` を esbuild でバンドルし、上記 HTML を入力して境界を出力した結果。

チャンク配分: **25.88% / 21.26% / 28.93% / 23.94%**

| 境界 | 前チャンク末尾 | 次チャンク先頭 |
|---|---|---|
| 0 | `…とどむるなかれ。 八二—八四<br>彼我に。` | `<ruby>幸</ruby>を愛する愛、その義務に缺くる…` |
| 1 | `…神のたふとき定は破れむ。` | `<br><br><br><span class="notes">［＃改ページ］</span><br><br><br><br>　　　第三十一曲` |
| 2 | `…【平和を愛する】マタイ、五・九。` | `<strong>惡しき怒り</strong>云々はその解にて…` |

**境界0 は行の途中で切れている。** 「彼我に。」で改行しているわけではなく、同じ行が `幸を愛する愛、…` と続く。句点の直後がたまたま `<ruby>` 要素だったため、そこが「段落の直後」と誤認された。ユーザーが懸念していた「数文字だけ書かれて次に続く」現象そのものである。

境界1 は結果的に章の変わり目付近だが、空行群と改ページ注記がすべて**次チャンクの先頭**に入っている。次チャンクの1ページ目は空行4行から始まる。

## 4. 原因

`scoreBoundary()`（`src/aozora-fallback/split.ts:174-184`）に3つの欠陥がある。

### 4.1 青空文庫の改ページ注記を認識していない

```ts
isPageBreak: tag === "hr" || /page/i.test(classAttr),   // split.ts:166
```

青空文庫リーダー HTML の改ページは `<span class="notes">［＃改ページ］</span>` というテキストとして残る。class は `notes` であって `page` を含まないため、**32箇所すべてが改ページとして認識されない**。tier 1（最優先）が一度も発火しない。

なお TXT アップロード経路では `packages/aozora-text/src/parse-document.ts:62-67` が `［＃改ページ］［＃改丁］［＃改見開き］［＃改段］` を正しく認識している。URL 経路だけがこの情報を捨てている。

### 4.2 連続 `<br>` の判定が空白テキストノードで壊れている

```ts
if (prev.isBr && i >= 2 && segments[i - 2].isBr) return 6;   // split.ts:182
```

実際の HTML は `<br>\r\n<br>\r\n<br>` であり、`<br>` の間に改行文字のテキストノードがある。`flattenSegments()` はこれを `textLen: 0` のセグメントとして保持する（`split.ts:119-132`、バイト等価な再構成のため意図的）。したがって segments 列は `[br, ws, br, ws, br]` となり、`segments[i-1].isBr && segments[i-2].isBr` は**成立しない**。

**tier 6 は、青空文庫リーダー HTML に対して構造的に一度も発火しない。**

### 4.3 「段落の直後」が行の途中にマッチする

```ts
if (prev.endsSentence) return 4;   // split.ts:180
```

`endsSentence` はテキストセグメントが `[。」』.!?]` で終わるかだけを見ており、**その直後が改行かどうかを見ていない**。`<br>` ベースの本文では「彼我に。幸を愛する愛…」のように句点の後に同じ行が続くことがあり、行の途中が段落境界と誤認される。これが境界0 の原因である。

さらに tier 4（文末）は tier 6（連続 `<br>`）より優先されるため、仮に 4.2 を直しても、章の切れ目より行途中の句点が優先されてしまう。

---

## 5. 目的・成功条件

- 分割境界を、原文で意味的に切れている位置（改ページ注記の直後 → 見出し → 空行 → 行末）に置く。
- 行の途中で切らない。切る場合は他に候補が皆無のときだけとする。
- 空行群を2つのチャンクに分断しない。空行は前チャンクの末尾に収め、次チャンクは実体のある内容から始める。
- チャンクの均等性を現状より悪化させない。
- 通常経路（フォールバックが発動しない変換）の出力を1バイトも変えない。
- TXT・EPUB・PDF アップロード経路、一般 Web ページに影響を与えない。

### 明示しておく限界

**余白ページそのものは消えない。** 4分割する以上、境界は3箇所あり、それぞれの前チャンク最終ページは途中で終わる。本改善が変えるのは「余白がどこに落ちるか」であって「余白が出るかどうか」ではない。改善後は章の終わりに余白が来るため、読者には「章末の空き」として自然に見える。

## 7. 変更内容

対象は `src/aozora-fallback/split.ts` のみ。他ファイルの変更は不要。

### 7.1 改ページ注記の定数を追加

ファイル先頭の定数群（`CHUNK_COUNT` の直前）に追加する。

```ts
/** 青空文庫リーダーHTMLに <span class="notes"> として残る改ページ注記。
 * TXT経路の parse-document.ts が認識する記法集合と同じもの。 */
const AOZORA_PAGE_BREAK_NOTE = /^［＃(改ページ|改丁|改見開き|改段)］$/;
```

`parse-document.ts:62-67` が認識する記法と集合を揃えること。片方だけ増やすと経路によって挙動が変わる。

### 7.2 `isPageBreak` の判定を拡張

`flattenSegments()` 内（現 `split.ts:166`）:

```ts
      isPageBreak:
        tag === "hr" ||
        /page/i.test(classAttr) ||
        AOZORA_PAGE_BREAK_NOTE.test((child.textContent ?? "").trim()),
```

`textContent` の前後空白を落としてから完全一致で判定する。部分一致にすると、注記を引用している本文（例:「［＃改ページ］と書かれた行」）を誤って改ページ扱いする。

### 7.3 ヘルパー関数を追加

`scoreBoundary()` の直前に置く。

```ts
/** 空白のみのセグメント（改行など）。textLen 0 かつ構造的な意味を持たない。 */
function isFiller(s: Segment): boolean {
  return (
    s.textLen === 0 && !s.isBr && !s.isBlock && !s.isHeading && !s.isPageBreak
  );
}

/** 境界 i の直前に連続する <br> の本数。空白のみのセグメントは数に入れず、
 * かつ連続を切らない（Aozora の reader HTML は <br>\r\n<br> と改行を挟む）。 */
function precedingBreakRun(segments: Segment[], i: number): number {
  let n = 0;
  for (let k = i - 1; k >= 0; k--) {
    const s = segments[k];
    if (s.isBr) {
      n++;
      continue;
    }
    if (isFiller(s)) continue;
    break;
  }
  return n;
}

/** 境界 i の直前にある、実体を持つ直近のセグメント（<br>・空白は飛ばす）。 */
function previousMeaningful(segments: Segment[], i: number): Segment | undefined {
  for (let k = i - 1; k >= 0; k--) {
    const s = segments[k];
    if (s.isBr || isFiller(s)) continue;
    return s;
  }
  return undefined;
}
```

### 7.4 `scoreBoundary()` を差し替え

```ts
/** Boundary "before segments[i]" priority score — lower wins. */
function scoreBoundary(segments: Segment[], i: number): number {
  const next = segments[i];
  const prev = previousMeaningful(segments, i);
  const brRun = precedingBreakRun(segments, i);
  // 境界の直後が <br>／空白だと空行群が2チャンクに分断され、次チャンクの
  // 先頭ページが空行から始まる。実体のあるセグメントの直前にだけ置く。
  if (next.isBr || isFiller(next)) return 9;
  if (prev?.isPageBreak === true) return 1;
  if (next.isHeading) return 2;
  if (next.isBlock) return 3;
  if (brRun >= 2) return 4; // 空行 = 章・段落の切れ目
  if (brRun === 1 && prev?.endsSentence === true) return 5; // 行末かつ文末
  if (brRun === 1) return 6; // 行末
  if (prev?.isBlock === true) return 7;
  return 8; // 行の途中 — 最後の手段
}
```

変更の要点:

| tier | 旧 | 新 |
|---:|---|---|
| 1 | 直前が改ページ（`hr` / class に page） | 直前の実体が改ページ（注記テキストを含む） |
| 2 | 次が見出し | 同左 |
| 3 | 次が div/section | 同左 |
| 4 | **直前テキストが文末** | **連続 `<br>` 2個以上（空行）** |
| 5 | 直前が div/section | 単一 `<br>` かつ直前が文末 |
| 6 | 連続 `<br>`（機能していない） | 単一 `<br>`（行末） |
| 7 | 任意 | 直前が div/section |
| 8 | — | 任意（行の途中） |
| 9 | — | `<br>`／空白の内部（実質除外） |

**tier 9 は必ず候補として残す。** `chooseBoundaries()` は候補が1つも無いと `best === -1` の縮退経路（`split.ts:222-235`）に落ちる。全境界を等しく評価可能に保つため、除外ではなく最低スコアとして扱うこと。

### 7.5 モジュール doc コメントの更新

`split.ts:8-44` の doc コメントは v3 仕様 §14 の8段階リストとの対応を説明している。上記の並べ替えに合わせて書き直すこと。特に「6. 連続br -> implemented directly (two consecutive `<br>`)」は事実と異なっていた（§4.2）ので、その旨と修正内容を残す。

| 空コンテンツでの固定エラーメッセージ | 通る | 同上 |

`scoreBoundary()` は非公開関数であり、テストから直接呼ばれていない。tier 番号の変更が外部に漏れることはない。

### 9.2 追加するテスト

`test/aozora-fallback/split.test.ts` に以下を追加する。

1. **改ページ注記の認識**: `<span class="notes">［＃改ページ］</span>` を含む fixture で、境界が注記の直後（＋後続の `<br>` 群の直後）に来ること。`［＃改丁］［＃改見開き］［＃改段］` も同様。
2. **注記の部分一致を拾わないこと**: 本文中に `［＃改ページ］と記された行` のような文字列があっても改ページ扱いしないこと。
3. **空白テキストノードを挟んだ連続 `<br>`**: `<br>\r\n<br>` が空行として認識され、tier 4 が発火すること（現行実装では発火しない回帰テスト）。
4. **行の途中で切らないこと**: 句点の直後に同じ行が続く fixture（`…彼我に。<ruby>…</ruby>を愛する愛…`）で、境界がそこに落ちないこと。
5. **空行群を分断しないこと**: 境界の前チャンク末尾が `<br>` で終わり、次チャンク先頭が `<br>` で始まらないこと。

fixture は浄火の構造（`div` なし・見出しなし・`<br>` 区切り）を模したものにする。既存テストの fixture は `div` を持つ構造が中心で、今回の欠陥を再現できない。

## 11. 実装順序

1. 作業用 worktree を作る。ベースは ref 名ではなく SHA を固定する（並行セッションが `origin/main` を動かすため）。
2. §7.1〜7.4 を適用する。
3. `npm test` で既存テストが通ることを確認する。落ちたケースがあれば、期待値を変える前に**なぜ落ちたか**を特定する（§9.1 の見込みが外れたということなので、原因を仕様書に反映する）。
4. §9.2 のテストを追加する。
5. §8.3 の手順で浄火 HTML を実測し、§8.1・§8.2 の数値が再現することを確認する。

## 13. 付随して発見した別課題（本タスクのスコープ外）

調査中に見つかった、本改善とは独立の問題。**この仕様書では扱わない。**

### 13.1 `［＃改ページ］` が PDF に印字されている

`<span class="notes">` は `src/printhtml.ts` の `STRIP_SELECTOR`（22-49行）に含まれず、`packages/aozora-text/src/styles.ts` にも `.notes` のスタイル指定がない。したがって青空文庫の注記テキストが本文と同じ書式で印字されている。

浄火の場合、`［＃改ページ］` が32箇所、外字注記（`［＃「さんずい＋幼」、60-8］` など）が6箇所、縦中横注記が4箇所、計42箇所。

これはフォールバック経路に限らず、**青空文庫 URL 経路すべてに影響する**。TXT 経路では `parse-document.ts` が注記を解釈して除去するため発生しない。URL 経路だけの問題。

対処するなら選択肢は2つ。(a) `printhtml.ts` で `span.notes` を除去する。(b) 注記の種類ごとに解釈する（改ページは改ページとして扱い、外字注記は残すなど）。(a) のほうが単純だが、外字注記のように読者にとって意味のある情報も消える。判断が要るため別途検討すること。

なお本仕様書の §7.2 は注記を**改ページ境界として認識する**だけで、印字の有無は変えない。13.1 を先に (a) で直すと `<span class="notes">` が DOM から消え、§7.2 が機能しなくなる。**両方を扱う場合は順序と相互作用に注意すること**（除去する前に改ページ情報を別の形で保持する必要がある）。

### 13.2 `Env` の doc コメントが 6003 に追随していない

`src/types.ts:333` と `src/feature-flags.ts:53-54` の `AOZORA_TIMEOUT_FALLBACK_ENABLED` の説明が「code 6002 の場合だけ」のままで、後から追加された 6003（PDF too large）に触れていない。コメントのみの不整合。
